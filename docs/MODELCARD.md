# API-OMNI-BRAIN trained parts (release needles-v1)

Three small models trained once for API-OMNI-BRAIN. **The router needle and (since 1.5.0, optional) the analyst are wired into the app; the sorter is not.** The router, with the weights installed, decides the class of content-classified requests (setting `needle_router`: off | shadow | active, default active) and falls back to the rules on any error, missing numpy, load or slow pass. Install: `API-OMNI-BRAIN --needles-install`, check: `API-OMNI-BRAIN --needles-test` (the single-file binary includes numpy since 1.4.0). The analyst: `API-OMNI-BRAIN --analyst-install [FILE]` (merged GGUF, Q8_0) and `--analyst-test`; the binary packs its own static llama-server, setting `analyst_local` off | fallback | prefer.

| file | what | base | licence of base |
|---|---|---|---|
| `router.npz` | classifies a request: code / json / de / reason (26M encoder-decoder) | Cactus-Compute/needle (rev 5f89b430) | MIT, Copyright (c) 2026 Cactus Compute |
| `sorter.npz` | capability of a model id: chat, code, vision, embedding, rerank, audio, image, video, safety, ocr, other | same | MIT |
| `needle.model` | the sentencepiece tokenizer of the needles | same | MIT |
| `analyst_adapter.tgz` | LoRA (r=32) for Qwen/Qwen3.5-0.8B-Base: use-case text -> required capabilities as JSON. Merged into a GGUF (Q8_0, 834 MB, release asset `analyst-v1`, wired as optional local analyst) | Qwen/Qwen3.5-0.8B-Base | Apache-2.0 |

`router.npz`/`sorter.npz` are float16 numpy archives (flat parameter names of the original checkpoint). The runtime is `omnipool/needle_rt.py` (numpy only, pure-Python tokenizer, scores the allowed answers instead of generating).

## Held-out results (authors never seen in training)
Labels come from the agreement of several judge/teacher models, so these numbers measure how well the model imitates that judgement, not absolute truth.
- router: acc 0.9852 (n=880), rule baseline 0.7159; weakest class code (recall 0.953). numpy runtime on 150 stratified rows: 148/150; end to end through the app's routing function on 300 held-out rows: 295/300 (rules alone about 0.72).
- sorter: acc 0.8514 (n=370), rule baseline 0.6432. On the 36 real OpenRouter model ids 0.9722 vs rule 0.9444, i.e. no real difference. Weak classes: other (0.25), image (0.545), vision (0.707).
- analyst: valid JSON 1.0, capability F1 0.8826 vs rule 0.4648 (n=176). The Q8_0 GGUF itself, measured separately through llama-server: F1 0.8835, exact match 0.7784, valid JSON 1.0 (same 176 rows). Q4_K_M and perturbation-consistency experiments are not measured yet.

## Honest limits
Training data is synthetic (generated by several free-tier LLMs, then filtered by multi-judge agreement; generated and real model ids mixed). The data itself is not published. About 40-80 ms per request on CPU (numpy, 2 BLAS threads, machine under load; first versions took 3 s because 16 BLAS threads fought for the cores). Use is at your own risk; the app's label stays "scripts + rules + statistics + an external judge" until a trained part is proven in real traffic; the router's gate so far is held-out agreement with teacher labels. The sorter is not wired in: 0.80 in the numpy runtime; on the 71 real model ids of the author's catalogue (2026-11-24) it disagrees with the rule on 9, and judged by hand the rule is right in 5, the sorter in 1, both wrong in 3. `tools/sorter_vs_rule.py` in the repo repeats this on your own catalogue.
